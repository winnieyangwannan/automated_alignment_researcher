### ARM64 cuSPARSELt packaging diagnosis

Question: How should the `nvidia-cusparselt-cu13` incompatibility be solved, and is “ARM64 branch” a Git branch?

Answer:

- ARM64 (`aarch64`) is the CPU architecture of the GB300 compute nodes, not a Git branch. The Git branch remains
  `uv`; its `pyproject.toml` contains environment markers that select ARM64-specific dependencies when running there.
- The locked wheel filename is correctly tagged `manylinux2014_aarch64`, and its native `libcusparseLt.so.0` is an
  ARM aarch64 ELF library. However, the wheel's internal `WHEEL` metadata incorrectly declares
  `manylinux2014_sbsa`. `uv` installs from the compatible filename but later rejects the internal `sbsa` tag during
  `uv pip check` and `uv sync --check`.
- This is currently a metadata consistency defect, not evidence that an x86 library is installed: PyTorch imports,
  detects the GB300, and executes CUDA operations successfully.
- Short-term workaround: retain the locked environment, allow only this exact known check failure, and keep the real
  import/CUDA smoke checks as the functional gate. Do not ignore any additional dependency errors.
- Durable fix: use an upstream corrected wheel or reproducibly repack the exact `0.8.1` wheel so both its filename and
  internal tag are `manylinux2014_aarch64`, publish it to an approved package/artifact source, point `uv` at it,
  regenerate the lock, recreate the environment, and rerun both dependency and GPU checks.
- Upgrading to a newer cuSPARSELt wheel is only an alternative after confirming compatibility because PyTorch 2.14.0
  declares an exact dependency on `nvidia-cusparselt-cu13==0.8.1`. Removing the package or installing an x86 wheel is
  not a safe workaround.
