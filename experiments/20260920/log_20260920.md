### Isolation boundary explanation

Question: What is the isolation boundary, and how does it work?

Answer:

- The autonomous researcher and evaluator are separate trust domains. The researcher may inspect code, train models,
  submit checkpoints, and read only permitted feedback. The evaluator alone may read hidden test items, answers,
  rubrics, full held-out scores, and judge credentials.
- The research side writes a checkpoint plus submission marker to `SUBMISSIONS_DIR`. A separately running evaluator
  worker reads that checkpoint and `HOLDOUT_DIR`, scores it, writes research-safe aggregate feedback to `SCORES_DIR`,
  and writes the complete held-out result to `HELDOUT_SCORES_DIR`. The researcher polls only `SCORES_DIR`.
- `EVAL_VIA_WORKER=true` prevents the research process from running evaluation inline. The held-out suite and full
  held-out scores must be owned by a distinct evaluator Unix/service identity with inaccessible parent directories
  (normally mode `700`). Shared handoff directories need narrowly assigned cross-user permissions.
- This protects against adaptive overfitting and leakage: an autonomous agent with shell access could otherwise read
  hidden answers, optimize directly against the held-out metric, or inspect its full score after every attempt.
- Merely using different paths, `.env` files, containers, or mode `700` under the same Unix UID is not a security
  boundary. The same UID can read or change its own files. Without a second evaluator identity, the setup is only an
  honor-system smoke test and its held-out result is not paper-valid evidence of generalization.
- Before launch, the research identity should pass `scripts/verify_heldout_isolation.sh`: evaluator-private paths are
  unreadable, the held-out identifier is absent from research-readable artifacts, and `held_out_pct` is absent from
  the shared score channel.

### Meaning of kernel-enforced isolation

Question: What does “kernel-enforced” mean?

Answer: Linux associates every process with a numeric user/group identity and checks that identity against file
ownership, permission bits, and ACLs whenever the process tries to traverse a directory or open, read, write, rename,
or delete a file. If an AAR process running as the research UID attempts to read an evaluator-owned mode-`700`
holdout directory, the kernel rejects the system call with `EACCES` before any bytes are returned. Changing prompts,
Python code, shell commands, or environment variables cannot override that check. Slurm jobs retain the submitting
user's identity on compute nodes, while a shared filesystem must resolve the same UIDs/GIDs consistently.

This is stronger than telling an agent not to inspect a path, hiding the pathname, or using two `.env` files under
one account. It does not protect against root/cluster administrators, a kernel vulnerability, incorrect permissions,
or credentials that let the research account become the evaluator. If both processes use the same UID, mode `700`
does not isolate them because the kernel sees the same owner.

### ACLs

Question: What are ACLs?

Answer: Filesystem Access Control Lists extend the normal owner/group/other permission bits by allowing rules for
specific named users and groups. For example, a submissions directory can grant the research user write access and
the evaluator read access, while a scores directory can reverse those roles. A default ACL makes new child files and
directories inherit the intended access. `getfacl <path>` displays the rules and `setfacl -m`/`setfacl -d -m` changes
access/default rules. The filesystem must support ACLs and resolve the same UIDs/GIDs on every cluster node.

ACLs do not create accounts, protect two processes using the same UID, or compensate for sudo/evaluator credentials
available to the research account. Also, the current repository writes research proposal metadata beneath
`SCORES_DIR/.proposals`; therefore making all of `SCORES_DIR` read-only to research would break the current code.
Either retain the repository-compatible shared-group write model or first move proposal metadata to a separate
research-writable directory before enforcing directional score ACLs.

### “Isolation is a deployment choice, not baked in”

Question: How does the statement in `PORTABILITY.md` relate to the earlier isolation discussion?

Answer: The core harness implements the logical split but does not create the security boundary. It always supports

separate evaluator account changes ownership, credentials, and path visibility while preserving the same transport

### How held-out result stripping is enforced in code

Question: How does the harness enforce stripping?

Answer:

- Composite evaluation first produces a full dictionary containing `held_out_pct` and `per_benchmark` entries. Each
  benchmark entry carries a role such as `safety`, `capability_filter`, or `held_out`.
- `aar.benchmarks.composite.strip_held_out()` makes a copy, deletes the top-level `held_out_pct`, removes every
  `per_benchmark` entry whose `role` is `held_out`, and applies the same filtering to nested `composite_scores`.
  `contains_held_out()` detects held-out content by the role annotation rather than value truthiness, so a zero or
  empty held-out result is still detected.
- `aar.eval_pod.run_eval` writes the stripped dictionary to its research-readable `--out` path and writes the full
  dictionary only to `HELDOUT_SCORES_DIR` with private permissions. If no private path exists, it discards the full
  held-out result rather than placing it in the shared output.
- `aar.eval_pod.entrypoint` repeats the boundary operation before `transport.put_scores()` writes
  `SCORES_DIR/<run_id>.json`. If saving the private full result fails, it replaces the research-facing payload with an
  error rather than risk publishing the full result.
- `aar.research_loop.tools.server_api_tools` strips again before returning `evaluate_model` output and before scores
  enter shared findings or leaderboard responses. This protects AAR-facing views even if an upstream result is
  unexpectedly unfiltered.
- `tests/test_smoke_orchestration.py::test_saturated_held_out_is_still_detected_and_stripped` covers removal of both
  the aggregate field and a role-tagged benchmark, including the empty-mapping edge case.

This is application-level information-flow enforcement, not filesystem isolation. It prevents the normal output path
from revealing held-out scores, but a same-UID research process can still bypass the application and read evaluator-
private files directly. That is why deployment isolation remains necessary for an adversarially robust experiment.

### Container/function isolation versus a trusted single user

Question: What do the two portability options—securely separated containers/functions and one trusted user—mean?

Answer:

- Secure container/function isolation runs research and evaluation in independently controlled execution identities.
  The research container/function receives the research code, its credentials, and the shared handoff volume only.
  The evaluator receives the shared handoff plus a separately mounted private holdout volume and evaluator secrets.
  The platform—not the research process—must control mounts, secret injection, and identity. Research must lack access
  to the container runtime/admin API, Docker socket, host filesystem, evaluator logs, evaluator image contents, and
  credentials that could launch or inspect evaluator workloads. Under those conditions, the platform rejects access
  much like separate Unix users do.
- Merely starting two Docker/Apptainer containers or two Slurm jobs from the same unrestricted HPC account is usually
  not secure isolation: that account can inspect its own files/jobs, relaunch a container with the private volume
  mounted, or otherwise exercise the same authority. A managed service such as separate Modal functions can provide a
  real boundary when volumes and secrets are scoped by the platform and the research function lacks control-plane
  access.
- A trusted-single-user deployment runs both roles under one UID. Separate directories, env files, processes, and the
  harness's stripping logic keep the workflow organized and prevent accidental disclosure through normal outputs,
  but nothing prevents the research process from directly reading the holdout/full scores if it has shell/filesystem
  access. “Trusted” therefore means assuming the researcher/agent follows the rules; it is an honor system.
- Both options use the same `SUBMISSIONS_DIR`/`SCORES_DIR` queue protocol. Secure containers/functions are suitable
  for defensible held-out generalization if correctly administered; single-user mode is suitable for development,
  baseline reproduction, and end-to-end smoke tests, but not an adversarially robust or paper-valid isolation claim.

### Modal and platform-scoped resources

Question: What is Modal, and what does it mean for secrets and volumes to be scoped by the platform?

Answer: Modal is a managed cloud compute service where an operator deploys Python functions that execute in separate
containers, optionally with GPUs, secrets, and persistent volumes. A volume is mounted storage; a secret is a managed
credential injected into selected functions at runtime. “Scoped by the platform” means the operator configures an
allowlist in Modal's control plane: the research function receives only its research credentials and shared handoff
volume, while the evaluator function additionally receives the private holdout volume and judge credentials. If the
research code asks the operating system for an unmounted holdout path or an uninjected secret, the resource simply is
not present in that execution environment.

This is analogous to two OS users only when the research function cannot access the platform administrator token,
Docker/control-plane API, evaluator logs, evaluator image, or a mechanism to relaunch itself with evaluator mounts.
Two locally launched containers controlled by the same unrestricted HPC user are generally organizational separation,
not a security boundary. Modal is only an example portability target, not a requirement or necessarily the right
choice for FAIR; external-service use and any data/model transfer require applicable Meta approval and policy review.

### Standalone librarian duration and tuning

Question: How long should `sbatch scripts/litreview.sh sycophancy syco-lit-v1 30` take, and is the duration tunable?

Answer: The repository's operational comment estimates roughly 40 minutes of running time for a fresh axis survey,
but no live librarian call has yet been timed on this HPC setup. Queue wait is additional and variable. The Slurm
script requests a two-hour wall-time limit; that is a maximum, not an expected duration. Four sub-area agents run
sequentially, each aiming for nine entries, followed by as many as four additional top-up agents if the valid unique
count remains below 30. API latency, web-tool behavior, rate limits, and top-ups determine the actual runtime.

The scheduler limit can be overridden without editing the script, for example
`sbatch --time=03:00:00 scripts/litreview.sh sycophancy syco-lit-v1 30`. Raising it only prevents premature Slurm
termination; it does not make the search faster. The third positional argument changes the minimum count, but lowering
30 does little to shorten a fresh run because the code always executes all four initial sub-area agents; it mainly
reduces the chance of top-up passes. The per-sub-area target (`--per`, default 9), four-sub-area set, sequential
execution, and four-attempt top-up cap are currently Python-level settings not exposed by `litreview.sh`. Meaningfully
shorter smoke searches would require adding wrapper arguments or a smoke profile rather than merely lowering the
minimum.

Recommended first run: retain the 30-entry target and two-hour limit, then use Slurm accounting to measure actual
elapsed time. If a baseline already contains at least 30 entries, `launch_team.sh` reuses it without another survey;
invoking standalone `litreview.sh` directly always performs the four initial passes and appends/deduplicates results.

### Monitoring a standalone librarian job

Question: What does `sacct -j <JOB_ID> --format=JobID,State,Elapsed` show, and how can the librarian be monitored in
real time?

Answer: `sacct` queries Slurm accounting for the specified job. `JobID` identifies the allocation and possible batch
steps, `State` reports outcomes/states such as `PENDING`, `RUNNING`, `COMPLETED`, `FAILED`, or `TIMEOUT`, and `Elapsed`
is wall-clock time used. It is best for historical/final accounting and may lag while a job is pending. For live
scheduler state use `squeue -j <JOB_ID> -o '%.18i %.9P %.20j %.8T %.10M %.10l %R'`, which shows elapsed time, time
limit, and the pending reason or assigned node.

The job's standard output is `slurm-aar-litreview-<JOB_ID>.out` in the directory from which `sbatch` was invoked.
`tail -F` can follow it before and after creation. The log streams phase starts/completions, agent text excerpts, tool
names such as `WebSearch`, `WebFetch`, and `share_literature`, entry counts, errors, top-up attempts, and the final
completion marker. It is progress telemetry, not necessarily the full contents of every paper record.

The actual records appear incrementally as atomic JSON files in `_runs/litreview/sycophancy/`. `watch` plus
`find ... -name '*.json' | wc -l` shows the raw file count; `ls -lt` shows newest records; and `jq` can inspect an
individual record while the job continues. The job writes each completed entry immediately rather than waiting until
the end. This explanation will be committed and synchronized from devserver `uv` to HPC `uv`; both begin at
`9064ca3`.
